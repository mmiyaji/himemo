# HiMemo v2 の暗号化とロック設計

管理者の QR 登録と暗号化索引の方針は [管理者端末登録と長期保存](egm-sync-v2-enrollment-and-scaling.md) に記載する。

## 鍵と権限

| 鍵 | 役割 | 端末間で使う方法 |
| --- | --- | --- |
| 同期鍵 | 変更ヘッダーと同期用メタデータを保護する | 同期に参加する端末で準備する。私用本文の鍵はここから作れない |
| プロファイル鍵 | 各プロファイルの本文・添付・検索用データを暗号化する | ランダムに生成し、プロファイルのパスフレーズで保護した鍵を同期する |
| 管理者鍵 | 全プライベートプロファイルの鍵を開ける | 同期鍵と独立した高エントロピーの復旧キーで管理者端末を登録する。登録端末では端末認証付きで保管する |

各プライベートプロファイルの鍵に、個別パスフレーズ経由と管理者鍵経由の二つの暗号化されたコピーを持つ。どちらのコピーにも同期アカウントの世代、プロファイル ID、鍵 ID、用途を認証付き暗号で結び付ける。通常プロファイルには端末間で復旧できる鍵を割り当てる。

管理者モードは登録済み端末で利用者の認証を要求し、全プロファイルを一括で開く。新端末は管理者として別途登録する。初版では、私用プロファイルの作成や ZIP からの新規プロファイル復元に管理者認証を要求し、二つの鍵のコピーがそろった状態で登録する。個別パスフレーズ変更は本文鍵を変更せず、その鍵を包み直す。過去に取得された鍵や平文の無効化は別の要件であり、鍵の失効・再暗号化の設計が必要になる。

OS の端末パスコードを他人と共有する端末では、その認証だけで管理者本人を区別できない。共有端末を対象にする場合は、管理者専用の認証を追加する。iPad で端末認証にひも付く保存を先に検証し、Web の管理者登録と鍵保持は別の受け入れ条件とする。

### 管理者モードの生体認証

- 登録済み端末ごとに、管理者認証を通したうえで「管理者モードを Face ID／Touch ID で解除」を有効・無効にできる。設定は端末ごとに保持する。
- 生体認証を選んだ場合、OS の認証に成功して初めて端末限定の保護領域から管理者鍵を取得できるようにする。iPad では現在の生体登録セットに結び付ける Keychain のアクセス制御（biometryCurrentSet / WhenPasscodeSetThisDeviceOnly）を使う。画面側の認証成功フラグだけで鍵を開けないようにする。
- 認証の取消し、失敗、端末の非対応、生体情報の再登録に備え、ADMIN復旧コードと、選択した場合の管理者専用パスフレーズによる解除経路を残す。共有端末の前提を考慮し、OS の端末パスコードには自動で切り替えない。生体情報の再登録後は管理者認証を経て設定し直す。
- QR と復旧コードは新端末の登録・復旧に使う。生体認証は登録済み端末での管理者モード開始に使い、個別プロファイルのパスフレーズによる解除は従来の設計に従う。
- 設定の有効化・無効化、認証取消し、登録セット変更、代替経路での解除、バックグラウンド移行後の再ロックを iPad で検証する。

[Apple の生体認証による Keychain 項目の保護](https://developer.apple.com/documentation/localauthentication/accessing-keychain-items-with-face-id-or-touch-id)

## 個別解除と同じパスフレーズ

- プロファイルごとに異なるランダムなソルトと、バージョン付きの Argon2id 設定を持つ。短い数字 PIN は同期可能な復号秘密に使わない。端末内の簡易 PIN や生体認証を提供する場合は、OS が守る端末限定の利便機能として分ける。
- 共通の解除画面では、入力を全候補の個別ラップに照合し、認証に成功したプロファイルをまとめて開く。最初の一致で処理を打ち切らない。個別指定画面でも同じルールを適用する。パスフレーズの一致を示す共有ハッシュや索引をクラウドに置かない。画面で開いた件数を表示する。
- 照合は画面を止めないように実行し、メモリ消費を抑えるため逐次処理または低並列にする。設定値は最も遅い対応端末と Web の両方で測る。試行制限は端末上の操作に効く。鍵の暗号化コピーまで取得された場合のオフライン推測に備え、長いパスフレーズを要求する。
- 解除セッションは開いたプロファイル ID の集合で管理する。管理者モード終了、手動ロック、アプリのバックグラウンド移行など所定の条件で、該当する鍵と復号済みの画面・キャッシュを破棄する。

## 同期、端末復旧、脅威モデル

- 管理者モードはバックグラウンド移行で再ロックする。個別プロファイルの自動ロック時間は利用者が設定する。
- ロック中のプライベートメモの記録日と件数は、端末の保存データやクラウド上の平文メタデータに載せない。記録月の索引はプロファイル鍵で保護する。暗号文のサイズや通信のタイミングから推測できる情報は別途評価する。

- 同期は暗号文とメタデータで進める。同期鍵を準備した新端末は、ロック中でも暗号文と鍵の暗号化コピーを受信し、同じ個別パスフレーズで解除できる。管理者としての登録は独立させる。
- ファイルや DB を外部ツールで開いても、ロック中の本文・添付・サムネイル・検索索引を平文で取得できないようにする。OS の共有・通知・検索、テンポラリファイル、診断ログにも平文を残さない。明示的なプレーン ZIP 書き出しは平文になる。解除中の画面を取得できる攻撃者や OS を掌握した攻撃者への防御は、保存時暗号化とは別の範囲になる。
- 同期鍵と管理者復旧キーは別々に復旧する。管理者復旧キーを失っても、個別パスフレーズを知っているプロファイルは個別に復旧できる。使える管理者端末、復旧キー、個別パスフレーズをすべて失ったプロファイルには復号手段がない。端末失効と鍵の再発行の効力は、既に取得済みのデータと将来のデータを分けて定義する。
- 旧 ZIP の取り込みでは、私用プロファイルを明示的な復元先に割り当て、端末内で再暗号化する。元データと照合して検証用の v2 世代に公開し、別端末で解除して本文と添付を確認してから、利用する世代を切り替える。

## 検証項目

- 同じパスフレーズを設定した二つのプロファイルが一度に開き、異なるパスフレーズのプロファイルは閉じたままになる。
- 新端末で個別パスフレーズによる解除と管理者登録後の全解除がそれぞれ成功する。同期鍵だけでは私用本文を取得できない。
- ロック中に編集済み暗号文を送受信できる。再ロック後にファイル、DB、検索索引、サムネイル、ログから平文を取得できない。
- パスフレーズ変更や新規プロファイル作成が中断されても鍵が失われない。復旧情報を失った場合の画面と手順が設計どおりに動く。

通常画面、私用鍵の配信、パスワードで暗号化した管理者鍵の端末内保存、試行制限、ロック中の送受信、バックグラウンドと画面退出時の私用鍵・管理者鍵の破棄を接続した。登録・復旧・中断再開・誤ったプロファイル鍵の拒否は自動テストで確認する。実機でのスナップショット、OS のファイル選択、Keychain の保持は受け入れ手順で別途確認する。生体認証は端末限定Keychainで管理者鍵を直接保護する。QR、全鍵の失効・再暗号化は初版に含めない。[鍵ラップの実装](../lib/features/security/data/sync_v2_profile_keys.dart) · [世代登録](../lib/features/sync/data/sync_v2_generation_registration.dart)

## 鍵導出の実行と性能確認

2026-11-15 に鍵ラップのポータブル形式へ、形式名、版番号、Argon2id の設定（メモリ65536KiB、反復3回、並列度4、出力32バイト、アルゴリズム版19＝0x13）を追加した。未知の版・設定、不正なソルト・AEAD の形式を鍵導出前に拒否する。私用プロファイルのパスワードは12文字以上、端末内管理者パスワードは任意方式で6文字以上とし、管理者・私用解除には永続的な試行制限を接続した。

通常メモの復旧用ラップは同期鍵でも開く。したがって、同期用復旧コードの取得者は通常メモを読める。私用プロファイル鍵をこのラップに入れてはならない。世代登録のサービスは通常プロファイル専用のランダムな鍵を生成し、同期鍵と管理者鍵に異なる認証対象でラップする。同期用復旧コードは管理者登録の代わりにはならない。復旧コードは秘密として扱い、ログや診断情報へ出さない。

メモの編集・削除は既知の全ての版と鍵を照合し、本文の暗号化と送信キューへの追加を v2 専用 DB の同じトランザクションで行う。鍵は認証済みの解除情報として世代・プロファイル ID に結び付け、新規メモや削除後の書き戻しでも別プロファイルの鍵を拒否する。既存のメモ DB へ複製する二重書き込みは導入していない。現在の検証は v2 専用 DB が対象であり、旧 DB の平文メタデータを取り除いたことを意味しない。

現行の v2 設定は Argon2id のメモリ64MiB、反復3回、並列度4。cryptography 2.9.0 の Dart 実装を使う。モバイルでは compute で別 isolate に移し、プロファイルごとの導出は順番に実行する。Web の compute は同じスレッドで動くため、ライブラリの協調的な待機があっても、応答性とメモリ上限は実測して判断する。Web Worker への移行と設定値の変更は計測結果を基に決める。

合成データだけを使う integration_test/sync_v2_key_performance_test.dart で、1件と3件の解除の所要時間とイベントループの最大応答間隔を記録する。iPad は実機で、Web は対象ブラウザで計測する。iPad のピークメモリは Instruments または DevTools、Web はブラウザのメモリプロファイラーで併せて測る。現時点で実機の時間とピークメモリは未測定。KDF 設定は鍵ラップの形式に属するため、速度だけを理由に暗黙に変えない。

2026-11-11 の開発環境では、Windows のテスト実行で3プロファイルの照合が731ms、イベントループの最大応答間隔は22msだった。Chrome のデバッグテストは、3件の鍵ラップ作成と3件の照合を含む全体が3分でタイムアウトした。照合だけの完了時間は得られていない。これをリリースビルドや iPad の値として扱わない。Web の v2 有効化前に、リリースビルドで再計測し、Worker または高速な暗号実装の導入とメモリ使用量を検証する。Windows の Flutter 3.47.8 の Web テストでは CanvasKit 配信が404になる問題があり、SDK内の同じファイルをテスト用ブラウザに供給して実行した。

参照資料は [Argon2id の仕様](https://www.rfc-editor.org/rfc/rfc9106.html) と [Apple の端末限定鍵保護](https://developer.apple.com/documentation/Security/protecting-keys-with-the-secure-enclave)。


### 生体認証と外部IDの責務

普段の管理者解除はFace ID／Touch IDでKeychainの管理者鍵を読む。初回も生体認証を選べば管理パスワードは不要。ADMINコードによる復旧はクラウド登録内のnormalAdminWrapで鍵を検証してから端末のKeychainへ登録する。生体認証が出す一時的なinactiveは画面を隠し、実際のpaused/hiddenは解除セッションを破棄する。遅れて返る認証結果で鍵を再投入しない。

iCloudのCloudKitアカウント、Sign in with Apple、Googleログインは管理者鍵と同一視しない。外部IDの認証トークンから鍵を導出しない。外部IDだけで新端末の鍵を復旧するには、別途キーエスクローまたは既存端末の承認方式が必要であり、現実装には含めない。生体鍵は端末間で同期せず、各端末でADMINコードから設定する。


### 管理者によるZIPの一括復元・上書き

一括復元はコントローラーが実際の管理者鍵を保持している場合だけ実行する。画面上の認証済みフラグだけでは実行しない。私用の復元先IDを同期鍵と取り込み元IDから、復元先鍵を管理者鍵と世代・取り込み元IDから用途別HMACで導出する。同期鍵だけでは私用の復元先鍵を導出できない。生成時はversion 2・mode admin-onlyの鍵ラップに管理者ラップだけを保存し、架空の私用パスワードやKDFを作らない。個別パスワードを後から設定すると、同じ鍵を従来のversion 1（パスワード＋管理者ラップ）へ移す。両端末を対応ビルドへ更新して利用する。

同じ元IDのメモの既知ヘッダーを親として新しい変更を作り、ZIPを正として復元する。以前の本文が欠落していても、認証済みのプロファイル鍵とヘッダーCASを確認して修復できる。未知ヘッダーの親・プロファイル整合性やZIPのCRC・パス・形式検査は維持する。メモIDはZIPや端末に依存させず、発行レコードには操作ごとのランダム値も用いて別端末の暗号文と衝突させない。既存の健全な添付参照は再利用する。

自動作成した私用プロファイル、メモ、添付、送信キューを一つのDBトランザクションで確定する。実際のバックグラウンド移行ではepochを失効させ、未確定処理をロールバックし、戻った認証結果で私用鍵を再投入しない。ZIPにないメモの削除は行わない。
